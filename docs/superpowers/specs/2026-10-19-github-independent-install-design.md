# 不依赖 GitHub 的客户安装方案

日期：2026-10-19

状态：第一阶段已在隔离分支实现完整离线包和本地安装流程；本地 Go、Bash
测试与真实 macOS MCP 握手已通过，Windows 运行验收仍需 CI。
自有在线下载服务尚未部署，也未推送、打标签或发布新版。

已确认的部署条件：目前没有可直接用于安装包分发的自有服务器、对象存储
或 CDN。按下文从零部署，不假设任何下载域名或存储已经可用。

## 目标与依据

客户即使无法访问 GitHub、GitHub API、raw.githubusercontent.com 和
GitHub 的资源跳转域名，也能完成安装和升级。首次只提供生图 API Key，
升级复用已有 Key；安装验证不产生生图费用。

截图中前两次失败发生在 Release API 检查（HTTP 403），第三次发生在
辅助脚本下载（传输连接提前结束）。403 的具体原因尚未确定，不能直接
归因为限流。源码确认当前说明、辅助脚本、源码包、二进制四个环节均依赖
GitHub；仅删除 API 检查无法解决整条链路的可用性问题。

## 方案比较

| 方案 | 优点 | 局限 | 决定 |
| --- | --- | --- | --- |
| 自有 HTTPS 下载源，提供各平台完整安装包 | 客户全程不访问 GitHub；一次包下载；支持离线交付 | 需要下载服务和自动同步发布流程 | 推荐 |
| 自有下载源镜像现有源码包和二进制 | 对现有安装器改动较少 | 仍需下载源码再下载二进制，版本配套和故障环节较多 | 仅作迁移备选 |
| 增加 GitHub 页面探测或公共加速代理 | 初期配置较少 | GitHub 不通时仍可能失败；额外探测增加等待；第三方代理不可控 | 不作为客户默认路径 |

## 推荐架构

GitHub 继续负责源码、构建和开发者 Release。发布任务把通过检查的同一批
安装包上传到维护者控制的下载服务，客户直接访问该服务。

下载服务需有有效 HTTPS 证书，支持普通文件 GET，不要求客户登录、
GitHub Token 或浏览器挑战；静态对象可由服务器或对象存储加 CDN 承载。
需用实际客户网络验证可达性，不能仅凭“CDN”或域名所在地判断。

当前推荐从对象存储起步，具体部署要求见下节。本文使用
`DOWNLOAD_ORIGIN` 表示待接入的自有 HTTPS 源，不代表地址已经上线。
下载源应与生图 API 的路径和发布权限隔离，避免静态下载影响生图服务。

下载源提供：

- `/image2/install/AGENT_INSTALL.md`：客户安装入口，不再引用 GitHub 文档。
- `/image2/stable.txt`：当前稳定版本及该版本引导文件和清单的路径、长度、SHA-256。
- `/image2/releases/<version>/bootstrap-agent-install.sh` 和 `.ps1`：固定版本辅助脚本。
- `/image2/releases/<version>/manifest.txt`：六个平台包的名称、版本、平台、长度和 SHA-256。
- `/image2/releases/<version>/image2-mcp_<os>_<arch>.<archive>`：六个完整安装包。

稳定入口可更新；版本目录发布后不可覆盖。Agent 读取稳定版本一次，之后
只使用选中的固定版本，避免执行途中混用两个版本。版本号、平台、文件名
均按固定规则校验，不能把清单中的任意 URL 或路径直接用于下载、写文件。

两个清单使用同一严格的 ASCII 记录格式：固定格式版本行、单一版本行和
文件记录。文件记录仅含规范相对路径、十进制长度和 64 位十六进制摘要，
每条字段数固定；重复、未知、缺失、额外字段及不规范路径全部拒绝。
由发布任务生成，客户端完整解析，不使用 grep 片段匹配，也不 source/eval。
这样 Bash 3.2 和 PowerShell 5.1 都可实现，不要求额外安装 JSON 解析器。
stable 必须完整列出两个引导文件及版本清单；版本清单必须完整列出六包。

## 从零部署要求

### 最小可用部署

推荐先开通面向客户所在网络的对象存储，绑定维护者控制的独立下载子域，
配置 HTTPS。初期无需购买云主机、数据库或开发下载后端；CDN 为按实测
结果增加的加速层，不是首发前提。网络较差时通过离线包交付。

| 项目 | 必需配置 | 验证方法 |
| --- | --- | --- |
| 域名和 DNS | 维护者有 DNS 管理权的独立下载子域；解析到存储下载入口 | 客户网络可解析；不复用生图 API 路径 |
| 对象存储 | 一个专用分发桶或容器，存储区域按客户网络实测选择 | 普通用户能读取公开发布对象 |
| HTTPS | 与下载域名匹配的有效证书和完整证书链，支持 TLS 1.2 | Windows PowerShell 5.1 和 macOS/Linux 均通过证书验证 |
| 读取策略 | 指定发布前缀匿名只读，无登录、Cookie、验证码或浏览器挑战 | 命令行 GET 返回文件原文，不能是状态 200 的拦截网页 |
| 发布策略 | 仅发布系统可写指定前缀；匿名用户不能写入或列出存储内容 | 匿名写入被拒绝；上传身份无修改桶权限的能力 |
| 缓存 | 稳定清单和安装说明使用再验证或禁止缓存；版本对象不可变 | 更新 stable 后新请求读到新值，旧版本仍可读 |
| 文件响应 | 文本文件可直接读取，压缩包按二进制传输；避免内容改写 | 远端实际 GET 的长度、SHA-256 与构建产物一致 |
| 发布记录 | 记录版本、提交、摘要、上传结果和稳定指针切换结果 | 可定位当前线上版本并恢复上一稳定指针 |

若选用中国大陆存储或 CDN 节点，部署前确认服务商的域名备案要求；区域
选择与证书配置由维护者完成，客户不需要办理或填写这些信息。不根据区域
名称承诺可达性，必须从实际客户使用的网络测通。

下载域名与任何回源地址都不能跳转回 GitHub。域名、证书和存储费用按服务商
实际报价确认；带宽费用按安装包大小、下载次数和计费规则估算，本方案不
假定免费额度足够。初期只配置一个已验证的官方源，避免为备用而重复采购。

### 开通后需要记录的维护者配置

- 下载源 HTTPS 根地址、存储区域、桶或容器名称、固定发布前缀。
- DNS 和证书的管理位置、续期方式，以及服务商要求的域名状态。
- 发布上传方式和最小权限身份：优先短期凭据或受限发布身份；需要长期
  凭据时放入 CI 的受保护 Secret，不写进仓库、安装说明或客户配置。
- 发布任务的并发锁及 stable 写入权限；恢复上一稳定指针的操作入口。

这些是维护者侧开通服务后填写的发布参数，不向客户索取，也不使用生图
API Key 代替上传凭据。离线包构建和安装器实现可以先行，不依赖这些参数。

### 部署执行顺序

1. 开通存储和下载子域，配置证书及公开只读策略，先上传一个无秘密的测试文件。
2. 在真实 Windows PowerShell 5.1、macOS/Linux 和客户常用网络进行直接 GET，
   验证 TLS、内容、下载耗时及没有 GitHub 跳转；失败时先解决该下载源问题。
3. 建立受限发布身份和 CI 参数，把完整安装包、脚本和清单上传到测试版本前缀，
   完成长度、摘要和缺文件检查；此时不切换对客入口。
4. 在阻断 GitHub 的环境中完成首次安装、旧版升级、失败回滚和 MCP 握手，
   再按发布流程启用正式版本与 stable。
5. 最后更新客服安装指令，保留离线包及上一稳定版本，按下载失败率决定是否
   增加 CDN 或第二个官方源。

在下载服务尚未开通期间，可先实现并验证离线完整包，再通过维护者受控渠道
交付。现有 v0.3.3 Release 六个资产仅包含程序二进制，不是本方案要求的完整
离线安装包；不得直接把它们作为已完成的离线安装方案交付。

## 客户安装流程

1. Agent 从自有下载入口读取安装说明和稳定版本，取得对应辅助脚本；
   检查长度和 SHA-256 后，以普通用户启动一次。
2. 辅助脚本识别系统和架构，从同一固定版本清单中选一个完整安装包。
   客户机器不查询 GitHub Release，也不逐个检查其他五个平台是否存在。
   在线辅助脚本接收稳定清单中选定的版本和清单摘要等非秘密参数，并在
   使用清单前校验摘要；这不改变首次 Key 仅由 stdin 输入的约束。
3. 下载到事务临时目录，校验包长度、SHA-256、平台和版本，检查压缩包
   路径、链接、重复项、大小写冲突及展开大小上限，再解压到暂存目录。
4. 完整包包含本平台二进制、安装脚本、runner、安装所需校验数据和许可证。
   客户不下载源码，不安装 Git、Go、Node 或 Python，平台安装脚本使用
   包内二进制，不能再调用下载逻辑或在包不完整时自动转为源码构建。
5. 复用现有目标所有权检查、配置快照、备份和事务替换逻辑。通过包校验后
   才读取或复用 Key；Key 通过现有附着进程 stdin 输入，禁止写入下载请求、
   命令行、日志或公开文件。包内安装保持离线，不向下载服务发送生图 Key。
6. 检查 runner、配置和实际 MCP initialize/tools-list，确认版本及
   `generate_image2`、`edit_image2`，通过后输出 `Verification: OK`。
7. 成功报告安装路径和旧版备份位置，提示重启 Codex 或开启新会话。

保留启动超时 20 秒、工具超时 600 秒；安装后的 MCP 启动使用本地文件，
不能依赖下载服务、GitHub 或检查更新请求。该方案不更改生图 API 的重试、
模型选择或 Image 2.5 路由。

SHA-256 用于检测损坏和版本混用；分发信任来自维护者控制的 HTTPS 源及
发布权限，不把同源摘要描述成独立数字签名。
Unix 使用已有 sha256sum、shasum 或兼容的 openssl 计算摘要，Windows 使用
系统 SHA-256 能力；缺少校验能力时明确报错，不自动安装依赖或跳过校验。

## 下载和错误处理

- 默认只有一个自有下载源，不自动探测 GitHub、公共镜像或修改代理。
- 每个源每个文件只请求一次，不自动循环重试，也不重新启动整个安装器。
- 说明、稳定清单和辅助脚本各有最多 15 秒的请求总时限；辅助脚本内清单
  请求最多 10 秒，包下载最多 60 秒，连接等待最多 5 秒。
- 辅助脚本内部所有网络操作共享 90 秒预算；后续请求只能使用剩余时间。
  该预算不包含用户等待输入 Key，也不声称覆盖整个 Agent 思考时间。
- PowerShell 5.1 需要实际可取消的请求总时限；不能只依赖读写空闲超时。
  继续启用 TLS 1.2，保留证书验证，报告 TLS/EOF、DNS、超时、HTTP 状态
  和失败阶段，禁止通过关闭证书校验来“修复”。
- 仅在维护者实际部署并验证了第二个官方源后启用一次备用切换，仍共享
  90 秒预算。备用文件必须属于相同固定版本且匹配已取得的长度和摘要；
  不重新读取 stable 来切换版本。完整性、平台、压缩包结构或权限校验
  失败直接停止，不以换源掩盖校验错误。
- 日志显示阶段、下载源、版本、错误类别和用时，不输出任何 Key。
  下载失败发生在目标变更和 Key 读取前；安装失败按事务恢复原目标和配置，
  恢复不完整时保留并报告证据。

## 离线交付

提供与在线版本相同的完整包和版本摘要文件，客服可以通过客户可达的
受控渠道交付。Agent 从维护者受控来源或客服交付的可信摘要取得预期值，
校验后调用包内离线安装入口；不能通过包内自带摘要证明包自身来源可信。
离线安装及 MCP 握手全程禁止网络调用。该入口沿用目标所有权、Key 保护、
配置快照和回滚；不能直接在任意目录执行旧版 installer 来冒充完整流程。
实际生图仍需客户能够访问现有图片网关。

## 旧版兼容

保留现有固定安装路径、旧版 byte-exact managed marker，以及已支持的
Git origin 所有权识别。新包若精简掉 go.mod 等源码文件，需要新增明确的
安装布局版本；验证器分别识别完整旧布局和完整新布局，不能简单放宽为
“存在目录就覆盖”。

升级保留原目录完整备份，安全复用 `.env.local`，只修改 image2 对应的
Codex 配置；其他 MCP 配置保持原样。升级失败恢复旧目标和完整配置。
不覆盖已经发布的 v0.3.3 标签或文件，新方案使用新的版本号。

## 发布流程

1. Linux 和 Windows 安装测试通过后构建六个平台二进制及完整安装包。
2. 生成固定版本清单，检查六包齐全且长度、摘要、平台、版本一致。
3. 从同一构建产物发布 GitHub Release 和自有源；先上传到唯一暂存前缀，
   校验后写入不可变版本前缀并逐文件读取核对。对象存储无需原子目录改名；
   stable 在此阶段仍指向旧版。
4. 对自有源实际执行 GET 校验，进行 macOS/Linux 和 Windows 在线安装、
   离线安装、升级及 MCP 握手冒烟。发布检查可以从维护者端访问 GitHub，
   不把这一职责下放给客户机器。
5. 所有目标验证完成后，通过单对象原子写入切换 stable.txt，并使用发布
   并发锁或条件写防止多个发布覆盖稳定指针；此前失败保持旧稳定版本。
   稳定指针使用短缓存或强制再验证，固定版本文件使用不可变缓存。
6. 自有安装说明、脚本和安装包均已可达后，才替换对客安装指令。

存储凭证仅存放在发布系统，不下发客户端。已有生图 API Key 不能用作
对象存储凭证或 GitHub Token。下载源未上线前不能宣称客户已可绕过 GitHub。

## 验收与落地顺序

先实现可重复构建的六平台完整包、离线安装入口、布局迁移和回滚测试；
再接入自有源、固定清单和严格下载预算；最后部署发布任务并验证真实客户
网络。运行时生图行为不在本次变更范围内。

关键验收：

- 将 GitHub 及其关联下载域名全部阻断后，在线安装和旧版升级仍成功。
- 离线完整包安装和 MCP 握手发起零网络请求、零生图请求。
- 403、429、5xx、DNS、EOF 和挂起连接按约定终止；请求记录证明没有循环
  重试或第二次安装，后备源只在明确配置时使用一次且不突破总预算。
- 清单/摘要/版本/平台不匹配，恶意压缩包、链接和目录冲突均在读取 Key、
  改动原目标之前失败；检查首次安装和升级两种情况。
- 首次只输入一次 Key；升级复用 Key；失败恢复配置；日志和公开对象无 Key。
- 在 Windows PowerShell 5.1、Windows ARM64、macOS 双架构和 Linux 双架构
  检查适用的平台行为；构建成功与真实系统安装通过分别记录。
- 缺任何平台文件、上传不完整、远端摘要不符或握手失败时，stable 不切换。

已确认当前没有下载基础设施，按“从零部署要求”开通并记录维护者发布参数。
上线以真实下载和安装验收为准；不把域名设想、已编译的二进制或仅在维护者
机器通过的测试视为客户下载链路已经可用。
